# AgentPay Vault 路演稿与 Demo 台本

> 默认时长：6 分钟演讲 + 2 分钟问答  
> 版本基线：2026-08-15 当前测试网实现  
> 原则：只讲代码已经证明的能力；未闭环部分主动标成下一步

## 1. 路演目标

评委离场时只需要记住三件事：

1. AgentPay 管的不是一次付款，而是 Agent 与服务商之间的一段资金关系；
2. 三种关系分别是连续服务、离散调用和任务交付；
3. Monad 让这些高频、低延迟、机器自主的结算关系具备可行性。

主线案例统一为：

> 一个研究 Agent 同时购买实时模型会话、数据 API 和最终研究报告。

不要逐个介绍“我们还有一个功能”。每个模块都必须回到同一个 Agent 的消费旅程。

## 2. 六分钟逐字稿

### 00:00–00:35｜问题

大家好，我们是 AgentPay Vault。

今天 AI Agent 已经可以自主调用模型、数据和工具，但机器支付不只有“一次请求、付一次钱”。一个研究 Agent 可能持续使用模型十分钟、调用数据 API 一万次，最后还要为一份研究报告在验收后付款。

真正缺少的是：钱先放在哪里，按什么粒度扣，服务失败后怎么退出。

### 00:35–01:05｜定位

x402 已经解决了 HTTP 请求如何提出支付要求、提交签名并完成单次结算。AgentPay Vault 向下增加一层长期资金关系状态机，把结算扩展到三种消费关系：

- 连续服务按时间结算；
- 离散调用按次数结算；
- 任务交付按状态结算。

一句话：**支付解决一次动作，AgentPay 管理一段经济关系。**

### 01:05–02:05｜Demo 1：Channel，主 Demo

【操作：滚动到“按次计量通道”，点击“开启通道”】

这是研究 Agent 的数据 API 预算。Agent 先锁定 `0.01 MON`，这是第一笔链上交易。

【操作：连续点击三次“调一次 API”】

现在发生了三次 API 调用，但每次只签一张 EIP-712 voucher，没有发送链上交易。voucher 记录的是累计金额，所以新 voucher 天然覆盖旧 voucher。

【操作：指向“离线调用次数”和“链上交易”计数】

三次调用，链上仍然只有开通道这一笔。即使是一万次调用，逻辑也一样。

【操作：点击“服务商拿最后一张 voucher 结算”】

服务商最终只提交最后一张 voucher，合约支付相对上次结算的增量。只在最后结算一次时，一万次调用可以压缩为开通道和结算两笔交易。

这不是我们声称发明的新协议；它与机器支付 Session 的累计 voucher 思路相同，我们在 Monad 上实现了自己的 EIP-712 状态机。

### 02:05–02:45｜Demo 2：Stream

【操作：滚动到“流支付金库”，点击“开启金库”】

如果 Agent 购买的是持续模型会话，按次计费也不自然。这里 Agent 预付押金，然后金额按秒归属给服务商。

【操作：指向实时增长的“已流动”金额】

合约不需要 keeper 每秒执行交易。应计金额通过区块时间直接计算；服务端也可以调用 `solvent()` 判断余额是否还能继续提供服务。

关闭时，已产生费用给服务商，剩余余额回到 Agent。

### 02:45–03:50｜Demo 3：Optimistic Escrow

【操作：滚动到“乐观托管 Escrow”，使用预先准备的 Delivered 状态】

第三种关系是任务交付。Agent 不是为一次请求付钱，而是为最终结果付钱。

资金先锁定。服务商在截止时间前提交交付凭证，系统开启争议窗口：

- Agent 满意，可以立即释放 100%；
- Agent 对结果有异议，可以触发预先约定的 50/50 退出；
- Agent 收到结果后装死，窗口结束后服务商可以取走 100%；
- 服务商始终不交付，超时后资金退回 Agent。

它不是仲裁系统，也不会判断报告质量。它是在没有仲裁者、没有额外抵押时，为小额机器任务提供一个确定、低协调成本的退出规则。

这里还有一个有趣的同构：Monad 执行层先乐观执行、冲突后纠正；我们的托管先乐观假设履约、争议时纠正。都是用事后纠错减少正常路径的协调成本。

### 03:50–04:45｜为什么是 Monad

【操作：打开 `/lens`，点击“并行执行这一批交易”】

当大量 Agent 同时给同一服务商结算，既有彼此独立的状态，也会出现大家争抢同一收入槽位的热状态。

这个模拟器按照 Monad 官方模型展示：交易先基于同一快照乐观并行执行；串行提交时，如果读到的输入已经失效，就覆盖重执行，最终结果与串行执行一致。

下面的 ConflictLab 会在真实测试网上制造热状态交易并展示同块打包和最终计数。它生成真实负载，但我们不会把“同块多笔”夸大成节点内部重执行的直接证明。

Monad 当前公开参数约为 400 毫秒区块、800 毫秒 finality；高吞吐和低延迟使机器请求与结算能处在同一个交互循环里。

### 04:45–05:15｜P256

【操作：返回首页，点击 P256 验证】

Agent 未来不一定使用浏览器钱包，它更可能使用 Secure Enclave 或 Passkey 类设备密钥。这里我们生成 P256 签名并直接调用 Monad `0x0100` precompile 验证。

当前这是独立能力验证，还没有接入 Escrow 主路径。下一步是把它变成 Agent 的受限授权密钥。

### 05:15–05:45｜商业与落地

我们的首批目标不是抽象的“所有 Agent”，而是已经在卖机器可调用服务的 Provider：模型推理、RPC、索引、数据 API 和 MCP 工具。

当前合约已经预留 Meter 结算抽成。下一步产品闭环是标准 x402 v2 接入、Provider relayer、双钱包角色面板和 USDC 结算。

### 05:45–06:00｜结尾

x402 让机器完成一次支付；AgentPay Vault 让钱理解时间、次数和交付状态。

**支付解决一次动作，AgentPay 管理一段经济关系。Monad 让这种关系能够以机器速度运行。**

## 3. Demo 操作清单

### 演示前 30 分钟

- 打开线上 Demo 和国内镜像，确认至少一个可访问；
- 钱包切到 Monad Testnet，余额不少于 1 MON；
- 确认三个合约地址与当前部署一致；
- 预建一个 Escrow 并完成 `deliver()`，让争议窗口在路演中自然结束；
- 另开标签页准备 `/lens`；
- 运行一次 UI 走查脚本并检查截图；
- 准备区块浏览器中的 Channel claim、Escrow claim 和 meter 交易；
- 关闭钱包弹窗以外的通知软件；
- 准备 90 秒录屏作为网络失败备份。

### 现场点击顺序

1. Channel：开通道 → 离线调用 3 次 → 最后一张 voucher 结算；
2. Stream：开启 → 保持流动；
3. Escrow：展示 Delivered → 讲四条退出路径 → claim 或 release；
4. `/lens`：运行动画 → 指出冲突和正确最终状态；
5. P256：签名 → precompile 验证；
6. 回到 Stream：关闭并讲清已结算与退款。

### 网络失败降级

- 一级：切国内镜像；
- 二级：展示预先打开的区块浏览器交易；
- 三级：播放 90 秒录屏；
- 四级：运行 `demo.mjs` 展示测试网 receipt；
- 不要在台上排查 RPC、钱包网络或 nonce。

## 4. 角色说明

当前 UI 为减少切钱包，把 Agent 和 Provider 使用同一连接地址。第一次执行资金操作前必须说：

> 为避免现场切换两个钱包，Demo 把买方和服务商折叠成同一地址；合约里的 payer/payee、agent/provider 权限仍然分离。今天展示的是状态机和真实链上交易。

## 5. Q&A

### 你们和 x402 有什么区别？

x402 已经覆盖单次 HTTP 支付的要求、签名、验证和结算。AgentPay 管理跨请求的资金关系，例如持续计费、批量调用预算和交付托管。当前 402 路由是自定义参考实现，标准 x402 v2 兼容是下一步。

### 为什么不直接每次 x402 支付？

单次结算适合低频、强终局请求。长会话需要时间计费，高频调用需要 voucher 聚合，任务服务需要验收和退出路径。它们不是同一个成本模型。

### Channel 是不是 MPP？

不是协议级兼容实现。它使用自定义 EIP-712 累计 voucher，设计语义与 Session 类支付相近。我们不会把概念相近说成已经兼容。

### 50/50 为什么公平？

它不是对事实的公平裁决，而是双方事先接受的确定性退出规则。优势是零仲裁、零额外抵押、低协调成本；代价是复杂争议保护有限。高价值交易应接 arbiter 或保证金策略。

### 服务商交垃圾怎么办？

Agent 在争议窗口内调用 `dispute()`，当前双方各取 50%。合约不判断内容质量；结果判断在链下，未来通过 arbiter hook、声誉或可验证计算增强。

### Agent 装死怎么办？

服务商交付后开启争议窗口；窗口结束无人争议，服务商调用 `claim()` 获得 100%。

### 为什么一定要 Monad？

Agent 支付是高频、低金额、低等待容忍的机器循环。Monad 的高吞吐、乐观并行执行、约 400ms 区块和 P256VERIFY 分别对应并发结算、热状态冲突、交互反馈和设备密钥授权。

### `/lens` 能证明 Monad 发生了重执行吗？

不能直接证明节点内部事件。上半部分严格模拟官方执行模型；下半部分生成真实热状态负载并验证最终计数。同块打包是性能观察，不是内部重执行证明。

### 现在是否真的 Agent 零 gas？

合约允许 Provider 或 relayer 持 Agent 签名调用 `meter()`，但当前首页由连接钱包提交交易，所以 UI 还没有完成独立 relayer 闭环。

### 商业模式是什么？

Meter 已有最高 5% 的协议费开关，默认关闭。后续收入包括统一结算抽成、Provider SDK、托管 relayer、对账和企业策略服务。当前不能宣称所有原语都已抽成。

### 能上主网吗？

这是测试网原型。主网前需要 USDC/SafeERC20、重入保护、权限与暂停机制、完整 invariant/fuzz 测试和外部审计。

## 7. 30 秒电梯稿

> AgentPay Vault 是 AI Agent 与数字服务商之间的链上结算状态机。x402 已经解决单次 HTTP 支付，但 Agent 还会持续使用模型、调用 API 一万次，或者为任务交付后付款。我们用 Stream、Meter/Channel 和 Optimistic Escrow 分别管理时间、次数和交付状态，并部署在 Monad 测试网。支付解决一次动作，AgentPay 管理一段经济关系。

## 8. 90 秒无 Demo 版本

> AI Agent 的支付不是一个按钮，而是一段持续关系。它可能运行十分钟、调用数据 API 一万次，也可能等待服务商交付一份报告。单次 HTTP 支付无法自然表达所有关系。
>
> AgentPay Vault 在 Monad 上提供三类结算状态机：Stream 按时间累计；Meter 和 Channel 按调用次数实时或批量结算；Optimistic Escrow 在任务交付后提供确认、争议、乐观取款和超时退款。
>
> 我们已经部署测试网合约、真实 402 参考路由、累计 voucher 通道、P256 验签面板和并行执行模拟器。我们也明确当前边界：还不是 x402 v2 或 MPP 协议兼容实现，P256 尚未进入主结算路径，UI 仍使用单钱包演示。
>
> 下一步是双钱包角色、Provider relayer、标准 x402 v2 和 USDC 主网加固。我们的核心判断是：支付解决一次动作，而 Agent 经济需要管理一段经济关系。
